$experimentMonitor = Get-Content -LiteralPath 'C:\Users\howie\Desktop\pa-csi-dg\docs\revision\monitor_config_20260930.json' -Raw | ConvertFrom-Json

只读检查器核对进程 PID 与创建时间、追加事件日志、日志更新时间和错误线索。运行期间不打开研究中不断替换的 status.json、progress.json、history.json、queue_status.json 或 queue_failure.json，也不读取活动检查点。不能把最后一条 running 日志视作进程仍在运行的证据。

每次检查发现进程消失即进入诊断；检查时若已有 20 分钟无训练/评估进展，视为疑似停滞，需要区分正常评估、GPU 忙碌、CPU 处理、磁盘等待及实际卡死。20 分钟是诊断阈值，定时检查间隔仍为 3 小时。不能只凭 GPU 利用率低或疑似停滞就杀死训练。所有源训练完成后，仍需核验目标评估和比较报告才算整批完成。

正常推进时保持安静。仅在发生中断、采取修复、恢复已验证、某批识别结果已核验、全队列完成或需要用户处理的阻碍时通知；通知去重，不每次重复同一问题。每次检查可以在 `D:/pa-csi-dg-revision-runtime/monitoring/full_revision_20260930/events.jsonl` 追加简短审计记录，此目录不属于冻结科学包。

## 再次中断时的处理

1. 先核对当前配置中的协调器、两个研究 runner 锁、子进程 PID 与创建时间，以及命令行中的实际 bundle。协调器消失而训练子进程仍活着时，先保护现有训练；不得启动重复训练，也不能因旧 PID 不存在而误判后来启动的进程。用户明确暂停或取消后不自动恢复。
2. 从追加 stderr/stdout 和事件日志定位错误。只有确认对应写入进程已停止，才读取该研究的可变状态、失败文件和 progress.json。保留原故障、日志、冻结哈希及最近检查点，建立新的恢复证据目录，不覆盖上次恢复档案。
3. 恢复前核对冻结 bundle/config/input/runtime/source split、采样计划和已完成任务的证据。以 progress.json 指向的已提交检查点为起点，验证 SHA256、模型和优化器可严格加载、随机状态、epoch/step/history 一致及有限数值。故障可能发生在检查点提交后、事件追加前，不得仅按最后一条 epoch 事件回退。不要机械重跑写死第 136 轮的旧审计脚本；它只是上次故障的审计实例。
4. 已确认的 Windows 文件替换错误、外部进程中断、陈旧锁等基础设施故障，在原冻结协议下主动修复并续跑。应用已验证的 `windows_atomic_retry_20260930.py`，保留仅限当前研究目录的同目录临时文件提交重试，默认 30 秒上限。确定失败标记已归档且根因已处理后，才能移走会阻止恢复的失败标记。任何文件移动都检查绝对路径范围；不删除失败证据，不伪造完成状态。
5. 新恢复使用独立的 coordinator 目录；可复用已验证包装器的 `run --directory ...` 和 `worker`，沿用原科学入口、18→27 串行次序及同一 GPU。旧脚本的 `start` 专门绑定上次的固定检查点，不能直接用于新故障。新目录复制并重新核对代码哈希与同一两个 bundle 哈希；记录恢复决策和启动身份，之后更新本目录的 monitor_config 指向新协调器。
6. 启动后必须确认新进程真实存活、恢复状态审计通过，并至少有后续 epoch 成功提交或评估阶段的新产物通过核验；仅得到 PID 不算恢复成功。恢复报告说明中断时刻、原因、恢复点、变化范围和核验依据。
7. 同一错误连续出现两次恢复失败时停止盲目重启，继续根因分析。数值异常、检查点损坏、输入/配置哈希变化、无法确定原进程状态或科学实现问题不能当作瞬时 I/O 错误跳过。能在已有授权内修复的继续处理；确需外部信息或改变科学实验定义时，保留现场并明确报告具体阻碍。
